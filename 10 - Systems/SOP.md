# SOP

## Objetivo

Documentar o “como fazemos aqui” em procedimentos claros, usáveis e versionados — para consistência, onboarding rápido e delegação sem perda de padrão.

Resolve conhecimento só na cabeça de uma pessoa, retrabalho e qualidade roleta.

---

## Filosofia

- SOP é ferramenta de execução, não romance documental.
- Se ninguém usa, não é SOP — é arquivo morto.
- Documente o que se repete ou o que quebra caro quando feito errado.
- Clareza > completude teatral. 1–2 páginas vencem manual de 40.
- SOP vive ao lado do trabalho (link no fluxo), não em pasta esquecida.
- Quem executa deve poder atualizar. Dono do SOP ≠ único que edita.
- Versão e data importam. SOP obsoleto é pior que ausência (falsa confiança).
- Automação come SOP repetível; SOP não compete com bom senso em exceção.

---

## Framework

### 1. Quando criar um SOP

Crie se ≥2 forem verdadeiros:

1. Tarefa se repete ≥ mensalmente
2. Erro custa caro (cliente, compliance, dinheiro, reputação)
3. Mais de uma pessoa pode/deverá executar
4. Onboarding precisa desse conhecimento
5. Você já explicou 3 vezes oralmente

Não crie SOP para experimento único.

### 2. Anatomia do SOP

```
Título + dono + última atualização
        ↓
Objetivo / quando usar
        ↓
Pré-requisitos (acessos, inputs)
        ↓
Passos numerados
        ↓
Definição de pronto (DoD)
        ↓
Exceções / escalation
        ↓
Métricas / SLA (se houver)
        ↓
Links relacionados
```

### 3. Padrão de escrita

- Frases imperativas curtas (“Abra X”, “Verifique Y”)
- Uma ação por passo
- Screenshots só quando reduzem erro
- Distinguir **must** vs **guideline**
- Incluir exemplo de input/output quando ajudar

### 4. Ciclo de vida

```
Dor / repetição identificada
        ↓
Draft pelo executor (não pelo teórico)
        ↓
Teste por segunda pessoa
        ↓
Publicar no hub
        ↓
Usar na operação
        ↓
Atualizar após incidente ou mudança
```

### 5. Biblioteca e governança

| Regra | Prática |
|-------|---------|
| Hub único | Índice por área |
| Dono | Nome + backup |
| Review | A cada trimestre ou pós-incidente |
| Aposentadoria | Arquivar com motivo |
| Descoberta | Link no ticket/playbook/ferramenta |

### 6. SOP vs Playbook vs Checklist

| Artefato | Uso |
|----------|-----|
| Playbook | Pensamento + framework (por que / como pensar) |
| SOP | Passo a passo operacional |
| Checklist | Verificação rápida na hora |

Não misture os três no mesmo doc sem estrutura.

## Aplicações

### SaaS

SOPs: onboarding de cliente, refund, incident response, release, churn save.

### IA

SOPs: eval run, prompt deploy, data labeling QA, rollback de modelo.

### Empresas B2B

SOPs: handoff AE→CS, mutual action plan, renovação, exception de desconto.

### Produtos Digitais

SOPs: release notes, moderação, app store submit, crash triage.

### Startups

Comece pelos 5 SOPs do caminho crítico de receita e retenção. Resto sob demanda.

## Erros Comuns

| Erro | Efeito | Correção |
|------|--------|----------|
| Novelas de processo | Ninguém lê | 1–2 páginas |
| Escrito por quem não executa | Irreal | Draft do operador |
| Sem dono | Decompose | DRI + review |
| Pasta caótica | Sumiu | Hub + índice |
| Nunca atualiza | Erro confiante | Data + trigger |
| SOP para tudo | Burocracia | Gate de criação |

---

## Checklist

- [ ] Dor/repetição justifica o SOP
- [ ] Dono e data visíveis
- [ ] Objetivo e quando usar claros
- [ ] Passos testáveis por outra pessoa
- [ ] DoD / output definido
- [ ] Escalation incluída
- [ ] Publicado no hub canônico
- [ ] Linkado no fluxo de trabalho
- [ ] Segunda pessoa validou
- [ ] Review date no calendário
