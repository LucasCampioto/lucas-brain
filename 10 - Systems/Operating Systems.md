# Operating Systems

## Objetivo

Desenhar o sistema operacional do negócio: cadências, donos, métricas e regras que fazem a empresa rodar sem depender de herói ou memória oral.

Resolve caos operacional — onde tudo é urgência, nada é processo e o crescimento aumenta atrito mais rápido que receita.

---

## Filosofia

- Empresa é um sistema de sistemas. Pessoas excelentes em sistema fraco sofrem.
- Operating System (OS) ≠ software. É o conjunto de rituais, artefatos e regras que produzem outcomes.
- Clareza de cadence vence motivação espontânea.
- O OS deve caber na cabeça do time: simples o suficiente para usar, completo o suficiente para escalar.
- Melhore o OS quando a dor é repetida — não quando está entediado de processar.
- Heróis apagando incêndio são sintoma de OS quebrado, não cultura admirável.
- Documente o caminho crítico do valor (como dinheiro e retenção acontecem).
- Estágio muda o OS. Copiar o OS de uma BigCo early-stage é obesidade processual.

## Framework

### 1. Mapa do OS (camadas)

```
Princípios / Operating Rules
        ↓
Estratégia trimestral (Quarter Planning)
        ↓
Cadências (semanal, mensal)
        ↓
Processos & SOPs
        ↓
Métricas & Dashboards
        ↓
Ferramentas & Automações
```

### 2. Cadences mínimas

| Cadência | Objetivo | Output |
|----------|----------|--------|
| Diária (leve) | Fluxo / bloqueios críticos | Unblock |
| Semanal | Prioridades + métricas | Weekly Review |
| Mensal | Tendências + capacidade | Ajustes |
| Trimestral | Apostas e alocação | Plano Q |
| Anual (leve) | Direção e tese | North star |

### 3. Elementos obrigatórios do OS

1. **DRIs** por área e métrica
2. **Single source of truth** (docs + números)
3. **Definition of done** por tipo de trabalho
4. **Escalation paths**
5. **Meeting policy** e async default
6. **Incident / postmortem** leve
7. **Hiring & performance gates** ligados à cultura

### 4. Como instalar (90 dias)

```
Semana 1–2: mapear como o valor flui hoje
        ↓
Semana 3–4: escolher cadências + DRIs
        ↓
Mês 2: SOPs dos 5 processos críticos
        ↓
Mês 3: dashboards + automações básicas
        ↓
Review: o que ainda depende de herói?
```

### 5. Stress test do OS

Pergunte:

- Se o fundador sumir 2 semanas, o que quebra?
- Que decisão se repete toda semana sem regra?
- Que métrica ninguém olha mas todos “acham importante”?
- Onde informação só vive no Slack?

### 6. Evolução por estágio

| Estágio | OS focus |
|---------|----------|
| 0–1 | Cadência semanal + scorecards + SOP dos loops críticos |
| 1–2 | Managers + dashboards + decision records |
| Scale | Políticas, career, compliance, automação ampla |

## Aplicações

### SaaS

OS centrado em ativação, retenção, NRR e pipeline. Cadência product-growth conjunta.

### IA

OS inclui eval cadence, data quality e incident de modelo — não só sprint de features.

### Empresas B2B

OS de revenue: forecast, handoff, QBR, renewals com donos claros.

### Produtos Digitais

OS de discovery→ship→learn com instrumentação. Content/release calendar integrado.

### Startups

OS mínimo viável: weekly review, 1 dashboard, 3 SOPs, decision log. Expanda sob dor.

## Erros Comuns

| Erro | Efeito | Correção |
|------|--------|----------|
| Zero cadência | Caos | Weekly + Q planning |
| Processos demais | Slowness | SÓ dor repetida |
| Métricas órfãs | Teatro | DRI por métrica |
| Tudo no fundador | Gargalo | Delegation + SOP |
| Copiar BigCo | Burocracia | Estágio-apropriado |
| Sem source of truth | Confusão | Canonizar docs/números |

## Checklist

- [ ] Fluxo de valor mapeado

- [ ] SOPs dos processos críticos

- [ ] Decision records para Tipo 1
- [ ] Meeting policy escrita
- [ ] Escalation path claro
- [ ] Stress test do “fundador ausente” feito
- [ ] Review trimestral do próprio OS
